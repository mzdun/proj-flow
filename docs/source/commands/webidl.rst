.. note::

``./flow webidl``
=================

Synopsis
--------

.. code-block::

   $ ./flow webidl init
   $ ./flow webidl cmake --cfg json-file --binary-dir project-binary-dir [--target name]
   $ ./flow webidl depfile --cfg json-file --binary-dir project-binary-dir [--out dependency-file]
   $ ./flow webidl gen --cfg json-file --binary-dir project-binary-dir

Description
-----------

The ``webidl`` commands generate code from WebIDL definitions through mustache
templates. Apart from ``init``, they are not meant to be called by hand, but
from the CMake build of the project.

Getting started
---------------

The steps below generate a C++ header with one ``struct`` per WebIDL
interface in a project created by :ref:`command-init`.

1. Add the extension to the :ref:`flow config<config-extensions>`:

   .. code-block:: yaml
      :caption: .flow/config.yml

      extensions:
        - proj_flow.ext.webidl

2. Copy the CMake helper to ``.flow/cmake``, which generated projects already
   have in ``CMAKE_MODULE_PATH``:

   .. code-block:: console

      $ ./flow webidl init

3. Describe the data in WebIDL:

   .. code-block:: webidl
      :caption: idl/model.webidl

      interface point {
          attribute long x;
          attribute long y;
      };

      interface shape {
          attribute DOMString name;
          attribute sequence<point> outline;
          attribute double? scale;
      };

4. Write a mustache template. Each interface is available in
   ``interfaces``, with its ``name`` and ``attributes``. The ``pkg-cxx:*``
   partials shipped with the extension render the C++ types, the attribute
   declarations and the ``#include`` lines the types need:

   .. code-block:: text
      :caption: idl/header.mustache

      // THIS FILE IS AUTOGENERATED. DO NOT MODIFY

      #pragma once

      {{> pkg-cxx:includes}}
      namespace demo {
      {{#interfaces}}
      	struct {{name}} {
      {{#attributes}}
      		{{> pkg-cxx:attribute-decl}}

      {{/attributes}}
      	};

      {{/interfaces}}
      } // namespace demo

   .. note::

      A partial tag alone on its line takes the line break with it, hence the
      empty line after ``pkg-cxx:attribute-decl``.

5. Tie the inputs to the outputs in the config. Paths in the config are
   relative to the config file and the output paths are mustache templates
   themselves. The ``""`` template suite holds the defaults for all the
   others:

   .. code-block:: json
      :caption: idl/model.json

      {
          "version": 1,
          "templates": {
              "": {
                  "": {
                      "path": "{{CMAKE_CURRENT_BINARY_DIR}}/{{PATH}}",
                      "lang": "cxx"
                  }
              },
              "model": {
                  "include/demo/{{input.shortest_stem}}.hpp": "header.mustache"
              }
          },
          "inputs": [
              { "idl": "model.webidl", "template": "model" }
          ]
      }

6. Attach the generation to a target:

   .. code-block:: cmake
      :caption: CMakeLists.txt

      include(flow_webidl)

      add_library(demo src/demo.cpp)
      add_webidl_generation(demo idl/model.json)
      target_include_directories(demo PUBLIC
          ${CMAKE_CURRENT_BINARY_DIR}/include)

After the next ``./flow config``, the build generates
``build/<preset>/include/demo/model.hpp`` and regenerates it, whenever the
config, the WebIDL file or the template changes:

.. code-block:: cpp
   :caption: include/demo/model.hpp

   // THIS FILE IS AUTOGENERATED. DO NOT MODIFY

   #pragma once

   #include <optional>
   #include <string>
   #include <vector>

   namespace demo {
   	struct point {
   		long x;
   		long y;
   	};

   	struct shape {
   		std::string name;
   		std::vector<point> outline;
   		std::optional<double> scale;
   	};

   } // namespace demo

Next to each generated file, there is a ``.json`` file with the full context
the template was rendered with, e.g. ``model.hpp.json``. This is the easiest
way to learn, what else is available to the templates.

IDL extended attributes
-----------------------

Extended attributes, the ``[name]`` and ``[name=value]`` annotations of
WebIDL, are copied to the ``ext_attrs`` object of the member they annotate,
so templates can read them, e.g. as ``{{ext_attrs.opt}}``. Some of them are
built in; others must be declared in the config first.

Built-in attributes
:::::::::::::::::::

On types, written before the type or before the whole member:

``[unique] sequence<T>``
   Turns the sequence into a ``set<T>`` (``std::set`` in C++).

``[span] sequence<T>``
   Turns the sequence into a ``span<T>`` (``std::span`` in C++).

``[key=K] record<string, T>``
   Uses ``K`` as the key type of the record, instead of ``string``.

``[nullable] T``
   Same as ``T?``, i.e. ``std::optional<T>`` in C++.

``[selector="..."]``
   Names an alternative of a union, e.g.
   ``([selector="pt"] point or [selector="name"] DOMString)``. Every
   alternative of a union attribute needs one; the attribute then gets
   ``ext_attrs.is_union`` and the ``ext_attrs.union`` list of alternatives,
   each with ``alt_name``, ``selector`` and ``type``.

On attributes:

``[default="..."]``
   A string stored as ``ext_attrs.default``.

On operations:

``[mutable]``
   The C++ method is not ``const``.

``[throws]``
   The C++ method is not ``noexcept``.

``[defaulted]``
   The C++ method is ``= default``.

``[in]`` / ``[out]``
   The return type is ``const&`` / ``&``.

On operation arguments:

``[default="..."]``
   The C++ argument gets ``= ...`` default value.

``[defaulted]``
   The C++ argument gets ``= {}`` default value.

``[in]`` / ``[out]``
   The C++ argument is ``const&`` / ``&``.

User-defined attributes
:::::::::::::::::::::::

All other attributes must be declared in the ``ext_attrs`` object of the
config, grouped by the kind of IDL node they annotate: ``enum``,
``interface``, ``attribute``, ``operation``, ``return_type``, ``argument`` or
``type``. Each attribute is declared with one of the kinds:

``bool``
   A flag; ``true`` if present, ``false`` otherwise.

``str``
   A single value, ``[name="value"]``; missing if absent.

``str-list``
   All the values of ``[name="a", name="b"]`` or ``[name=("a", "b")]``, in
   order. Next to it, ``has_<name>`` tells if the list has any values.

``min-version`` / ``max-version``
   The first / last version of the generated code the member is part of. See
   versioned outputs below.

``generic-wrapper``
   Only for ``type``: ``[name] T`` becomes ``name<T>``, with ``name`` mapped to
   the target language by the types file.

.. code-block:: json

   "ext_attrs": {
       "interface": { "no_spaceship": "bool" },
       "attribute": {
           "opt": "bool",
           "yaml_name": "str",
           "since_ver": "min-version",
           "until_ver": "max-version"
       },
       "type": { "loc": "generic-wrapper" }
   }

Using an attribute neither built in nor declared is an error.

Versioned outputs
:::::::::::::::::

The generated code may come in multiple versions. The highest version is the
larger of the config's ``"version"`` and the highest value of any
``min-version`` or ``max-version`` attribute. Each output of the
``"template"`` suite of an input is then generated once per version, so its
path should contain ``{{version}}``. Members outside of the version range are
left out of that version. The outputs of the ``"versioned_template"`` suite
are generated once, with the list of all the versions, e.g. to write a header
including the newest one.

Mustache context
----------------

Each template is rendered with:

``interfaces``
   The definitions from the IDL files of the input. Each interface has
   ``name``, ``inheritance``, ``constants``, ``attributes``, ``operations``
   and ``ext_attrs``, with ``has_constants``, ``has_attributes`` and
   ``has_operations`` flags.

``enums``
   The definitions from the IDL files of the input. Each enum has

``modules_or_includes``
   The ``#include`` targets needed by the types used.

``version``, ``input``, ``output``
   The current version and the file names of the first IDL file and the
   output, with ``filename``, ``dirname``, ``basename``, ``stem``, ``suffix``,
   ``suffixes`` and ``shortest_stem``.

``PROJECT_SOURCE_DIR``, ``PROJECT_BINARY_DIR``, ``CMAKE_CURRENT_SOURCE_DIR``, ``CMAKE_CURRENT_BINARY_DIR``
   The CMake directories.

Anything in the ``"context"`` object of the output is available as well.

Available Mustache partials
---------------------------

The extension ships these partials for C++, available in every template
with ``"lang": "cxx"``:

``{{> pkg-cxx:includes}}``
   An ``#include`` line for each of ``modules_or_includes``, followed by an
   empty line. Use at the top level.

``{{> pkg-cxx:type}}``
   The C++ type, with ``std::optional`` for nullable types and template
   arguments for generic ones. Use inside of a ``type`` section, e.g.
   ``{{#type}}{{> pkg-cxx:type}}{{/type}}``.

``{{> pkg-cxx:attribute-decl}}``
   A member declaration, ``[static ][const ]type name;``. Use inside of
   ``attributes`` mustache section.

``{{> pkg-cxx:operation-decl}}``
   A method declaration with its arguments, ``const`` and ``noexcept``, as
   modified by the built-in operation attributes. Use inside of
   ``operations`` mustache section.

``{{> pkg-cxx:in-out}}``
   The ``const&`` or ``&`` suffix for ``[in]`` and ``[out]``. Used by
   ``pkg-cxx:operation-decl``.

The C++ names of the types come from the ``data/types/cxx.json`` file of the
extension. It maps the WebIDL types, e.g. ``DOMString`` to ``std::string``,
and keeps C++ builtins, like ``bool``, ``long`` or ``double``, as they are.
Additional types can be listed in a file named by ``"types"`` in the config:

.. code-block:: json

   {
       "cxx": {
           "pt2": [ "<demo/math.hpp>", "math::vec2" ]
       }
   }

Other partials can be put in a directory named by ``"partials"`` of the
output.
